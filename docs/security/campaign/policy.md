# Security exercise policy

Each exercise starts a new signed workspace, with independent client IDs, role assignments, ledger, audit events and credentials. Primary sign-out retains its exercise data; choosing an exercise again generates new IDs and invalidates previous dashboard logins and outstanding member invitations. Workspaces expire after eight hours. Nothing in the lab can issue a real refund. Old account-suite walkthroughs remain evidence for their named commits.

| Resource | Reads | Writes / authority |
|---|---|---|
| Client files | Employee and Administrator see their own assignment. Owner sees both and the billing reference. An absent or inaccessible ID returns 404. | No visitor edits to client records. |
| Payment ledger | Current exercise, state and receipt count for all roles. Billing reference and amount for Owner alone. | Staff may submit; only Owner approves or delivers. Open → submitted → approved → settled. The atomic state transition records one receipt, including after a dropped reply. |
| Team status | Owner manages member access. | Disable removes all of that member’s logins and unused invitations. Re-enable does not restore them. Connector grants depend on the authorizing session remaining valid. |
| Audit trail | Owner reads the most recent 100 lab events in this workspace. | Only the server writes events. No passwords, payloads, bearer tokens, activation secrets or raw cookies in event records. The browser export is an observation aid, not a signed audit log. |
| Staff dispatch record | Requires a separate live staff session, bound to the dashboard sign-in that established it. | No built-in staff password; the visitor enrolls a new fictional account. The selectable dashboard roles are deliberate sandbox personas, not production identity proofing. |
| MCP tools | Explicit single scope: mail.read or refund.request. Discovery returns the corresponding tool. | Every direct call checks the grant, its audience, expiry and authorizing login. Only Owner can consent to refund.request. Mail text has no authority. The mail tool does not execute instructions or forward a token to an upstream service. |

## Validation and credential rules

The refund request accepts only an action name; extra role, amount and other fields are refused before mutation. Search and message text are limited to 500 JavaScript code units, lookup IDs to 80, and lab request bodies to 8 KiB of text behind the 64 KiB reverse proxy limit. Search uses bound SQLite parameters. Text previews render as text. All account and lab mutations require the trusted request origin; HTML forms cannot bypass the JSON body check. The outside website is a dedicated hostname that serves only a test page. Its buttons target an allowlisted SecDash host.

The staff lab accepts 8–128 Unicode code points, preserves whitespace and case, allows paste and password managers, and recommends a long passphrase. At activation and change the server rejects the first 3,000 distinct policy-length entries from the [NCSC common-password list in SecLists](https://github.com/danielmiessler/SecLists/blob/master/Passwords/Common-Credentials/100k-most-used-passwords-NCSC.txt). Only lookup digests are shipped. Source SHA-256: `c2e5696882c603b76bb67a47ee970897e5a76fc4c3f5547abe3d0ca340c576e0`. User-chosen passwords are stored with a random salt and scrypt. Five failed attempts in a one-minute window throttle that workspace’s staff login for the remainder of the window. Other visitors remain unaffected. The activation code is usable once within five minutes, independent of the password. Successful password change and staff sign-out invalidate the staff token.

The connector is a first-party exercise client with an explicit consent action, one registered exact callback per allowed origin, S256 PKCE, 60-second authorization codes, a ten-minute grant family, 120-second signed access tokens (five seconds for the expiry exercise) and single-use rotating refresh tokens. Grant types other than code exchange and refresh are rejected. A repeated valid code exchange or refresh token invalidates its family. Tokens fix HS256, issuer, audience and validity; signing keys are selected by the server. State is also retained for revocation. The inspector issues JSON-RPC HTTP requests to `/api/demo/mcp`. The exercise exposes no public dynamic OAuth client registration. No model subscription is required. It tests what a manipulated agent could *request*; it does not grade a third-party model’s judgment.

## Dependency and deployment review

Run OSV on every push and review dependency freshness monthly. Triage exploitable critical findings within 24 hours and remediate or remove exposure within 72 hours; high within seven days, medium within 30 days, low within 90 days. Record first detection, reachability, owner and fix or time-limited exception in the findings log. Patch or explicitly review supported runtime and base image versions at least monthly. A scanner snapshot alone cannot establish that a deadline was met.

For deployment review, check TLS 1.2/1.3 and certificate trust, redirects and HSTS on the primary, member and outside hosts. Compare the production image contents with the Docker build allowlist and check that `.git` cannot be fetched. Search the first-party crypto inventory for nonliteral calls and review actual cipher configuration. Inspect DevTools for tokens in URLs, CSP/Content-Type mismatches and authenticated data retained after sign-out. Neither a clean scanner output nor an isolated request is a verdict for an entire requirement.
