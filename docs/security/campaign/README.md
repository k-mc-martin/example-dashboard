# SecDash manual review (optional)

[Launch the exercise picker](https://vps-ca027b84.vps.ovh.us/launch) · [Deployed commit](https://vps-ca027b84.vps.ovh.us/version) · [Campaign CI](https://github.com/k-mc-martin/example-dashboard/actions/workflows/campaign.yml) · [Scanner evidence](https://github.com/k-mc-martin/example-dashboard/actions/workflows/security-tools.yml) · [Rules and limits](policy.md)

Under **Explore an exercise yourself**, choose a card and select **Start exercise**. Sign in as Mira (Employee), Theo (Administrator), or Inez (Owner). For Theo’s Administrator checks, follow exercises **1, 2, 5, and 6** in the [exercise directory](#exercise-directory). The exercise opens on its first dashboard screen. For exercises 8, 13, and 15, select **Inspect evidence** to open **Verification results** directly. **Sign out** changes identity within the same exercise. **Teams** lets the Owner open a member in another tab of that workspace. A private browser window represents an independent visitor. Selecting a card under **Choose another exercise** starts a fresh workspace.

For each review, compare **Latest server response** with the expected outcome in the table. For a denied change, inspect the affected record or ledger afterward. Try the allowed action as well, so you can see that the operation works for an authorized caller. For evidence reviews, compare the displayed checks with the GitHub run for the same commit. You can record the build, date, browser, role, steps, expected and observed outcomes, and a redacted evidence reference in [the blank results sheet](manual-results.csv).

Before starting another exercise, select **Download exercise report (PDF)**. It records the build, time, identity, server receipt, HTTP status, and relevant returned fields. Payment receipts also show the resulting ledger state and provider refund count. The Owner can export receipts across roles in the same workspace. For an automated run, use **Run all 19 exercises** on the picker. When it finishes, select **Download suite results (PDF)** for the per-exercise verdicts and operation details. The walkthroughs below describe expected behavior. Record your manual verdict from the result you observe.

## ASVS requirement checklist

The checklist maps all 70 OWASP ASVS 5.0.0 Level 1 requirements to an exercise or a scope decision. Use the linked build evidence and your own observations to assess each requirement. For a scope exclusion, record why it applies to the reviewed build. Earlier manual verdicts identify their tested commit and controls in the [account log](../accounts.md#manual-verification-log).

### Bad-input attacks

| ASVS 5.0.0 | Exercise | Review criterion |
|---|---|---|
| 1.2.1 | 16 | Verify that output encoding for an HTTP response, HTML document, or XML document is relevant for the context required, such as encoding the relevant characters for HTML elements, HTML attributes, HTML comments, CSS, or HTTP header fields, to avoid changing the message or document structure. |
| 1.2.2 | 16 | Verify that when dynamically building URLs, untrusted data is encoded according to its context (e.g., URL encoding or base64url encoding for query or path parameters). Ensure that only safe URL protocols are permitted (e.g., disallow javascript: or data:). |
| 1.2.3 | 16 | Verify that output encoding or escaping is used when dynamically building JavaScript content (including JSON), to avoid changing the message or document structure (to avoid JavaScript and JSON injection). |
| 1.2.4 | 16 | Verify that data selection or database queries (e.g., SQL, HQL, NoSQL, Cypher) use parameterized queries, ORMs, entity frameworks, or are otherwise protected from SQL Injection and other database injection attacks. This is also relevant when writing stored procedures. |
| 1.2.5 | 16 | Verify that the application protects against OS command injection and that operating system calls use parameterized OS queries or use contextual command line output encoding. |
| 1.3.2 | 16 | Verify that the application avoids the use of eval() or other dynamic code execution features such as Spring Expression Language (SpEL). Where there is no alternative, any user input being included must be sanitized before being executed. |

| 3.2.2 | 16 | Verify that content intended to be displayed as text, rather than rendered as HTML, is handled using safe rendering functions (such as createTextNode or textContent) to prevent unintended execution of content such as HTML or JavaScript. |

For L1 and L2 applications, refresh token rotation may be used. If refresh token rotation is used, the authorization server must invalidate the refresh token after usage, and revoke all refresh tokens for that authorization if an already used and invalidated refresh token is provided. |
