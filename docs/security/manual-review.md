# Review the four account controls

[Launch Dupdash](https://vps-ca027b84.vps.ovh.us/launch) and open the [deployed commit](https://vps-ca027b84.vps.ovh.us/version). Follow the source link in that response to inspect the exact deployed version. On GitHub, press the period key to open that revision in the browser editor. For desktop VS Code, open the cloned repository and compare its checked-out commit with the deployed SHA.

Start with **Sign in as Owner**. Wait for the fictional records to load. Under **Teams**, select Mira and open her session in a second tab. You can keep Owner open and use Mira’s tab to check what an employee sees. Theo provides an Administrator comparison. A private browser window gives you a second visitor workspace.

| ASVS 5.0.0 | What to do | Evidence to record |
|---|---|---|
| **7.2.3 · Session tokens** | In VS Code open [the session issuer](../../lib/demo-login.ts). Trace both the primary login in `issueLogin` and the member login in `enterMemberTab`. Check which random generator each uses, how many bytes it requests, and whether it generates a fresh token each time. Convert bytes to bits by multiplying by eight. Compare with the ASVS minimum of 128 bits. | Commit, functions, generator, and bit count. Record source references without copying live token values. |
| **7.4.4 · Sign out** | For each role, visit every section it can reach, including Teams for Owner. Look for **Sign out** on each screen. Follow links that open authenticated pages in a new tab, including the sample release site. Try signing out in the employee tab, then revisit a restricted view. | Record which screens had visible sign-out access, any exceptions, and what happened in each tab. |
| **8.1.1 · Role and record permissions** | Compare the [written access policy](accounts.md) with the [server’s route and role rules](../../lib/demo-permissions.ts) and [authorization checks](../../lib/server-auth.ts). Check permissions for individual operations and records. For a concrete example, grant Mira storage viewing while leaving backup creation off, then check both actions as Mira. Include the rule protecting another visitor’s records. | For each rule, record the role, resource, action, expected result and observed result. Record any missing or ambiguous policy, even if a test passes. |
| **8.1.2 · Field permissions** | Compare the documented read **and write** restrictions with each shared API. In Chrome open **View → Developer → Developer Tools → Network**, select **Fetch/XHR**, and refresh. Click a request, then **Response**. Compare the same feed as Owner and Employee. For example, check whether `providerConnections` appears in the inbox response and which fields a storage viewer receives from the recovery feed. In Teams, inspect the permission update under **Payload** and trace which fields the server will accept. | List the covered feeds and editable fields, role or resource conditions, and any undocumented or unexpected fields. Begin with the [inbox handler](../../app/api/dashboard/route.ts), [operations handler](../../app/api/operations/route.ts) and [Teams handler](../../app/api/demo/teams/route.ts). |

Use the [session requirements](https://github.com/OWASP/ASVS/blob/v5.0.0_release/5.0/en/0x16-V7-Session-Management.md) and [authorization requirements](https://github.com/OWASP/ASVS/blob/v5.0.0_release/5.0/en/0x17-V8-Authorization.md) as the criteria.

## Record your result

Add your observations to the [manual verification log](accounts.md#manual-verification-log). For each row include the requirement ID, your name or reviewer handle, date, commit, environment, steps, expected and observed behavior, and a verdict. Use **Pass**, **Fail**, or **Not yet tested**. If a check covers only a subset of screens or feeds, list the remaining scope. For an exception, link the relevant source or a screenshot with session values removed. The project owner’s November 10 verdicts and follow-up notes are in the [hosted review log](accounts.md#hosted-account-review-november-10-2026).
